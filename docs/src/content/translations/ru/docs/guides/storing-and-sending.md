Каждый тип сериализуется в стандартную строку ISO 8601 при преобразовании в текст или передаче в `JSON.stringify()`. На принимающей стороне эти строки напрямую разбираются обратно соответствующей фабричной функцией.

## JSON и форматы передачи данных

Передавайте значения напрямую в `JSON.stringify()` без пользовательских сериализаторов и обёрток:

```js
import { date, duration, time } from 'native-dates';

const standup = date('2026-11-16').at('9:30am', 'America/Los_Angeles');

JSON.stringify({
  startsAt: standup,
  dueOn: date('2026-11-16'),
  opensAt: time('9:30am'),
  length: duration('1h 30m'),
});
// '{"startsAt":"2026-11-16T17:30:00.000Z","dueOn":"2026-11-16","opensAt":"09:30:00","length":"PT1H30M"}'
```

| Тип | Строка для передачи | Типичное поле в данных |
|---|---|---|
| [`DateTime`](/api/date-time/) | `'2026-11-16T17:30:00.000Z'` | Метки аудита, вылеты рейсов и запланированные встречи |
| [`CalendarDate`](/api/calendar-date/) | `'2026-11-16'` | Сроки оплаты, праздники и даты бронирования |
| [`Time`](/api/time/) | `'09:30:00'` | Часы работы магазинов и время ежедневных напоминаний |
| [`Duration`](/api/duration/) | `'PT1H30M'` | Таймауты, SLA, расчётные интервалы и таймеры |
| [`YearMonth`](/api/year-month/) | `'2026-11'` | Расчётные периоды, сроки действия карт и поля выбора месяца |
| [`MonthDay`](/api/month-day/) | `'10-17'` | Повторяющиеся дни рождения и ежегодные праздники без года |
| [Диапазоны](/api/ranges/) | `'2026-11-01/2026-11-07'` | Окна бронирования, спринты и интервалы ISO 8601 через слеш |

Если внешнему API, ключу кэша или целочисленному столбцу требуется число, получите отсчёт от эпохи Unix в нужной единице. Имя каждого свойства явно указывает единицу, так как одни системы считают в секундах, а другие — в миллисекундах:

```js
standup.toString(); // '2026-11-16T17:30:00.000Z'
standup.epochSeconds; // 1794850200
standup.epochMilliseconds; // 1794850200000
duration('1h 30m').toMilliseconds(); // 5400000
```

## Обратное преобразование в код

При чтении ответов JSON, строк базы данных или параметров URL передавайте каждую строку обратно в соответствующую фабричную функцию:

```js
import { date, dateRange, datetime, duration, time, yearMonth } from 'native-dates';

const startsAt = datetime('2026-11-16T17:30:00.000Z', 'America/Los_Angeles');
const dueOn = date('2026-11-16');
const opensAt = time('09:30:00');
const length = duration('PT1H30M');
const billing = yearMonth('2026-11');
const window = dateRange('2026-11-01/2026-11-07');
```

Любой `DateTime` сериализуется в UTC, поэтому два клиента, зафиксировавшие одно и то же событие, получают одинаковые строки. Передача часового пояса при обратном разборе показывает тот же момент UTC в местном времени, не сдвигая само событие.

## Будущие и повторяющиеся события

Для прошедших событий — квитанций об оплате или серверных логов — достаточно одной метки времени в UTC. Для будущих событий, запланированных пользователем, рядом с меткой времени нужно сохранять поле `zone` с часовым поясом IANA.

```js
import { date, datetime } from 'native-dates';

const standup = date('2026-11-16').at('9:30am', 'America/Los_Angeles');
const row = {
  startsAt: standup.toString(),
  zone: standup.zone, // 'America/Los_Angeles'
};

const nextWeek = datetime(row.startsAt, row.zone).plus(1, 'week');
nextWeek.hour; // 9
```

Если часовой пояс сохранён, прибавление недель или месяцев удерживает местное время 9:30 при переходе на летнее или зимнее время. Такой подход также автоматически учитывает будущие изменения часовых поясов, принятые законодательно.

:::tip[Храните имена IANA, а не смещения]
Смещение вроде `'-08:00'` описывает только зимнее время в Лос-Анджелесе. Сохраняйте `zone` везде, где будущая календарная арифметика должна учитывать местный сезонный перевод часов.
:::

## Столбцы базы данных

Подбирайте тип столбца SQL под тип значения, чтобы база данных соблюдала те же ограничения, что и код приложения.

| Тип | Столбец SQL | Почему подходит |
|---|---|---|
| `DateTime` | `timestamptz` или `bigint` | Хранит точный момент времени в UTC без неоднозначностей |
| `CalendarDate` | `date` | Хранит `YYYY-MM-DD` без полуночных сдвигов из-за часового пояса |
| `Time` | `time` | Хранит `HH:MM:SS` без выдумывания фиктивной даты |
| `Duration` | `interval` или `text` | Хранит структурированные интервалы или строки ISO 8601 вида `PT` |

Избегайте столбцов SQL `timestamp` без часового пояса для реальных моментов времени: драйверы баз данных часто трактуют такие метки в локальном часовом поясе сервера.

## HTML-поля ввода и URL

Стандартные HTML-элементы ввода даты, месяца и времени принимают и возвращают те же самые строки ISO, что и типы ядра. Тот же компактный формат подходит для параметров строки запроса URL.

```js
import { date, time, yearMonth } from 'native-dates';

// <input type="date" value="2026-11-16">
const due = date('2026-11-16');
due.toString(); // '2026-11-16'

// <input type="month" value="2026-11">
const billing = yearMonth('2026-11');
billing.toString(); // '2026-11'

// <input type="time" value="09:30">
const opens = time('09:30');
opens.toString().slice(0, 5); // '09:30'

const params = new URLSearchParams({ from: due.toString() });
params.toString(); // 'from=2026-11-16'
```

Разбор полей даты через [`date()`](/api/date-fn/) также избавляет от классической ошибки `new Date('2026-11-16')`, когда полночь по UTC в часовых поясах Западного полушария сдвигается на предыдущий день.
